### 5.3 Run-splitting rule (exact; implemented in code, never by hand or by an LLM)
Input is the raw string, as a sequence of Unicode code points. Output is the tagged text.

**Step A, classify each code point:**
| Class | Code points | Assigned font |
|---|---|---|
| **A** (Arabic script) | U+0600–U+06FF, U+0750–U+077F, U+08A0–U+08FF, U+FB50–U+FDFF, U+FE70–U+FEFF. This includes Arabic letters, harakat (U+064B–U+065F, U+0670), shadda, tatweel U+0640, Arabic-Indic digits U+0660–U+0669, ٪ U+066A, ، U+060C, ؟ U+061F | Noto Sans Arabic |
| **L** (Latin, digits, punctuation) | U+0021–U+007E (ASCII printable except space: Latin letters, ASCII digits 0–9, `"` `(` `)` and all other ASCII punctuation and symbols); U+00A1–U+024F except U+00AD (Latin-1 Supplement letters and punctuation, Latin Extended-A/B); U+2010–U+2027 and U+2030–U+205E (General Punctuation without spaces, format and bidi controls; includes the en dash U+2013) | Noto Sans |
| **S** (space) | U+0020 only | resolved in Step B |
| **X** (anything else) | e.g. U+00A0, U+00AD, U+200B–U+200F, U+061C, U+202A–U+202E, U+2066–U+2069, emoji, other scripts, combining marks outside the A ranges | none. **Pre-render check fails → INVALID** |

**Step B, resolve spaces.** Take each maximal run of consecutive S characters. Let `left` be the class of the nearest character before the run and `right` the class of the nearest character after it, both A or L (the run has no neighbour on a side at the string edge). If `left` and `right` both exist and are equal, every space in the run gets that class. In every other case (the neighbours differ, or the run touches a string edge) the spaces get **A**, the style default.

**Step C, emit tags.** Scan left to right in logical order, starting with the "current font" set to A (the style font). Before each character whose class differs from the current font, emit `{\fnNoto Sans}` (switching to L) or `{\fnNoto Sans Arabic}` (switching to A), then update the current font. Never emit a tag at the end of the string. Adjacent identical classes form one run, so no tag is emitted between them.

**Consequences for the neutral characters named in the brief.** ASCII digits are L, even where Noto Sans Arabic also covers them (AR-04, AR-05); this follows the Founder decision. Arabic-Indic digits are A. `"` `(` `)` are L, and bidi mirroring is still computed by FriBidi/HarfBuzz from the RTL context, not from the font. The en dash is L. ٪ ، ؟ ـ are A. A space between two Latin-font characters stays in Noto Sans ("iPhone 16 Pro"). A space at an Arabic/Latin boundary is in Noto Sans Arabic.

**Assumption Engineering must confirm (consultation item E1):** in libass 0.17.1, `\fn` overrides split HarfBuzz shaping runs only, while FriBidi bidi resolution and paragraph direction (`Encoding: -1`) are computed over the whole event text, so the tags do not change visual order. Every switch falls at a non-joining boundary (space, quote, bracket, dash, or a digit next to a space), so no Arabic joining pair is ever split across fonts.

## 6. Metrics and thresholds (set NOW, never changed after; kept from EXP-006 §6)
**Definition of "correct" for one string (EXP-006 §6, unchanged unless creative-lead objects at consultation):** creative-lead judges string i correct (`correct_i = 1`) only if it records **no Sev-1 defect, no Sev-2 defect, and no defect of any severity in the property that string is designed to test** (column "What it tests"). Sev-3 defects in properties a string does not test are recorded but do not by themselves make it incorrect. Tofu or missing glyphs and clipped text count as Sev-1.

**Font-switch consistency (category "font-switch", decided at consultation H-0011).** At every boundary between a Noto Sans run and a Noto Sans Arabic run, the judge compares the two runs and records:
- **Sev-1:** glyphs of the two runs overlap or collide, any glyph is clipped, or the boundary space has gone (words run together). These count as Sev-1 under the existing clipping, tofu and order rules.
- **Sev-2:** (a) the baseline of the Latin/digit run visibly steps up or down from the Arabic baseline, so the line reads as two lines or as a superscript or subscript; or (b) the Latin cap height or ASCII digit height is above 1.3× or below 0.6× the height of Arabic alef (ا) in the same line, so it reads as a different text size; or (c) the stroke weight differs enough that one run reads as bold next to regular.
- **Sev-3:** any smaller visible difference in size, weight, spacing or dash/quote vertical position (for example the en dash in AR-10 sitting higher or lower than the digits' mid-height).

Font-switch consistency is **not** part of the tested property of any string. A Sev-3 font-switch note alone does not make a string incorrect. Sev-1 or Sev-2 does, under the general rule. For each boundary, the judge writes the estimated height ratio or baseline offset in the note, as a number, and never as "looks off".

| Metric | Threshold for "pass" | Threshold for "kill" (= FAIL) |
|---|---|---|
| `N_correct` (strings judged correct, of 10) | = 10 | ≤ 9 |
| `N_sev1` (Sev-1 defects, all strings) | = 0 | ≥ 1 |
| **Verdict** (Founder-fixed rule) | **PASS iff `N_correct` = 10 AND `N_sev1` = 0** | **FAIL otherwise** |
| Gating: `cov_ok`, `ctrl_ok`, `log_ok` | all True | any False → **INVALID** (no verdict) |

There is no "neither" zone. INVALID is not a verdict; it means the measurement did not happen as specified.

## 8. Deviations policy and threats to validity
Any change from §5 is listed in the results, never hidden.

**Invalidating (result = INVALID):**
- Any precondition in §5.1 fails, including a font sha256 mismatch or `fc-match` resolving elsewhere.
- A raw-string or tagged-text fingerprint does not match §4 or §5.3; any class-X code point.
- `COVERAGE_OK=False` for any of the 10 strings.
- `ctrl_ok` = False after the allowed instrument fixes (below).
- **Any glyph resolved to a file not in the declared set**, as shown by a FLAGGED log (rule (b)); or any `Glyph … not found` line (rule (a)) for one of the 10 strings, even when the fallback file is a declared one. That case means a character went to the wrong font of the pair, contrary to §5.3.
- Any §5.2 parameter or the §5.3 rule changed; any override tag other than the two allowed.
- A PNG missing or not 1080×1920; the instrument hash at step 9 ≠ the hash at step 1.
- The judge is not creative-lead; judging without 200% zoom or without the raw reference; the judge has seen any EXP-006 or EXP-008-control PNG.

**Instrument defects found by the controls (steps 4 to 6), before any of the 10 real strings is rendered:** the instrument code may be fixed to match this specification, max 2 times (company retry rule). Each fix is logged with the new instrument hash, then steps 1 to 6 are re-run from a clean `render/exp007/`. A fix may change code only, never this specification. If the specification itself turns out to be wrong, that needs a new EXP id.

**Re-execution rule (as EXP-006):** an execution error found before any PNG has been shown to the judge allows up to 2 identical re-executions of §5.4, each logged. **Once any PNG has been judged, the result stands.** There is no re-render and no re-judging until it passes.

**Non-invalidating, recorded:** library patch versions different from §3; byte-identical PNGs with EXP-006 for AR-01/02/03/06/07/09 (expected); log warnings that are neither rule (a) nor rule (b).
